# Review guidelines

These are the invariants reviewers (human and automated) should check on every
pull request to protovalidate-es. Formatting and lint are enforced by Biome in
CI, so reviews should not comment on style.

## Generated and vendored code

- Files under `packages/*/src/gen` are generated by `protoc-gen-es`. Do not
  review their contents line by line, and never accept hand edits to them.
- If generated output changes, the PR must also include the change that caused
  it, usually a `.proto` input or a `buf.gen.yaml`. Regenerate with
  `npx turbo run generate`.
- `packages/protovalidate/proto` is copied from upstream protovalidate. It must
  only change together with `packages/upstream/version.txt`.

## Runtime: `packages/protovalidate`

This is `@bufbuild/protovalidate`, published to npm and used in browsers,
Node.js, Deno, and Bun.

- **Public API.** Flag any change to exported API surface: `src/index.ts` and
  the `gen/buf/validate/validate_pb.js` export. Removals, signature changes,
  and behavior changes are breaking and need explicit justification. Every
  public API change must be called out in the PR description.
- **Dependencies.** Flag new dependencies, and changes that loosen the exact
  pins on `@bufbuild/cel` and `@bufbuild/re2`. Flag use of `@bufbuild/protobuf`
  APIs that are not available across the whole peer dependency range.
- **Portability.** Flag Node-only runtime dependencies (`node:*` imports,
  `Buffer`, `process`) in non-test code, and anything not available in baseline
  browsers from the last 2.5 years.
- **Bundle size.** Flag top-level side effects and patterns that defeat
  tree-shaking. Small bundle size matters for browser users.
- **Spec correctness.** Rule semantics must match the CEL expressions in
  `validate.proto` and the upstream conformance suite. Question any change to
  how a rule is evaluated, which violations it reports, or the IDs, messages,
  and paths of those violations.
- **Native rules.** A change to a native rule in `src/native` must keep it
  equivalent to the CEL expression it replaces. A change to rule planning or
  the CEL path must keep native rules equivalent too. Flag any divergence.
- **Untrusted input.** Validation often runs on untrusted messages. Flag
  evaluation cost that is worse than linear in the size of the message,
  unbounded recursion or allocation, and any user-supplied pattern evaluated
  with the JavaScript `RegExp` engine instead of RE2.

## Conformance: `packages/protovalidate-testing`

- Any entry added to `expected-failures.yaml` is a conformance regression. Flag
  it and require a justification in the PR description.
- The conformance suite runs both with native rules and with
  `PROTOVALIDATE_DISABLE_NATIVE_RULES=1`. Changes must pass both.

## Upstream: `packages/upstream`

- A change to `version.txt` updates the upstream protos, the conformance suite,
  and the README. The PR must include the regenerated code and README, and
  explain any new or removed expected failures.

## Benchmarks: `packages/protovalidate-bench`

- PRs that claim a performance improvement should include benchmark results
  from this package, before and after the change.

## Tests

These conventions apply to tests written by contributors and to generated tests.

- **Location.** Tests live next to the code they test as `*.test.ts` in
  `packages/protovalidate/src`. Shared helpers for native rule tests are in
  `src/native/testing.ts`. Test-only code must not be reachable from
  `src/index.ts`, so it never ships in the published package.
- **Framework.** Use `node:test` (`suite`, `test`) and `node:assert`. Tests run
  via `tsx --test`. Do not introduce Jest, Vitest, or other test dependencies.
- **Message fixtures.** Use generated messages or compile an inline proto with
  the existing helpers. Never hand-construct descriptor objects.
- **Native rules.** Tests for a native rule should check that it reports the
  same violations as the CEL path for the same input.
- **Regressions.** Bug fixes need a test that fails without the fix. If the bug
  has an issue, reference it in the test name.
- **License header.** Every new test file needs the Apache 2.0 header. CI
  enforces this.
